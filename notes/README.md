# Format notes

Everything this project knows about file formats lives here, not in code comments. Code points
to the relevant section, for example `// see notes/containers.md#compound-file-signature`.

## Clean-room rules

Every contributor, human or agent, works under these rules. If a task seems to need breaking
one, stop and ask a maintainer.

1. Learn formats only by inspecting files. Never disassemble, decompile, debug, or hook a
   vendor program or its libraries.
2. Use no vendor SDKs or APIs, and do not run vendor software to convert files during
   development or tests.
3. Do not search for, open, or use leaked source code, SDKs, or internal documentation. If
   something found online looks like it came from a vendor's internals, ignore it and report it
   (see "Flagging material" below).
4. Skip encrypted or password-protected data and log the reason. Never try to break it.
5. Use only clean test files: self-made by a licensed contributor, under an explicit open
   license, or synthetic (generated by our tools or written by hand from a public spec). Record
   every file in `corpus/manifest.csv`.
   **Owner-approved exception (2026-11-15):** sample drawings that Autodesk publishes for
   download may be used locally as `vendor-sample` files. They live in the gitignored
   `corpus/vendor/`, only their metadata is committed, and they are never redistributed.
6. Check and record the license of every library and published spec before relying on it, in
   [licenses.md](licenses.md).
7. Use vendor names factually only ("reads SolidWorks files"); no logos or marks.
8. Record how every finding was made, using the template below.

## Finding template

Each format file (`notes/<format>.md`) has one section per fact:

```markdown
## <short-anchor-name>

**Claim:** what is true about the format.
**Status:** hypothesis | confirmed
**Evidence:** corpus paths (from corpus/manifest.csv) or a published spec section.
**Method:** how it was observed, e.g. "compared streams of a.sldprt and b.sldprt saved
twice from the same model with a hex diff; offsets 0x40-0x47 changed with the thumbnail".
**Versions:** software versions the claim was checked against.
```

A claim stays a hypothesis until it is checked against real sample files from at least the
versions listed. Synthetic fixtures can show that our parser follows a spec; they cannot confirm
that vendor files do.

## Flagging material

If a source looks like vendor-internal material (leaked headers, SDK dumps, confidential
documents), do not read further, do not copy anything from it, and open an issue that names
the URL and why it looks suspect. Maintainers decide what happens next.
